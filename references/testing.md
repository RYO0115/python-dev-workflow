# テストの詳細方針

## いつテストを追加するか

機能を**追加・修正・削除**したら毎回。純粋な内部リファクタ（外部の振る舞いが変わらない）だけは対象外。判断に迷ったら追加する。

## テストの種類の使い分け

| 検証したいもの | 種類 | 例のツール |
|---------------|------|-----------|
| ブラウザでの見た目・操作（HTMX/JS の挙動含む） | UI テスト | Playwright |
| ロジック単体を決定的に検証（ランダム性・日時条件など UI 越しでは検証しづらいもの） | ユニットテスト | pytest |

推奨ディレクトリ構成:

```
tests/
├── unit/     # サービス層など、決定的なロジックの単体テスト
└── ui/       # ブラウザ操作・表示のテスト
```

## 完了前の確認

- `uv run pytest` を実行して**全テスト green** を確認してから完了報告する。
- テストが落ちている場合は、出力を添えて落ちている事実を正直に報告する。

## 既存テストとの関係

- 変更が既存テストの対象範囲内なら、新規ファイルを作らず既存テストを修正する。
- テスト一覧ドキュメントがあるプロジェクトでは、追加・変更したテストケースを追記する。

## テストが固定するのは「目的」だけにする

実装の書き方まで固定したテストは、無関係な変更で落ちて往復を生み、しかも本当に守りたい性質は
守れていないことが多い。

- **宣言や出力の完全一致で固定しない。** 生成 CSS の `.band{a:1;b:2;c:3}` を末尾まで一致で見ると、
  無関係なプロパティを 1 つ足しただけで落ちる。守りたいプロパティ・値だけを検査する。
- **部分文字列の検査には境界を付ける。** `"data-lang" not in html` は、後から足した
  `data-lang-path` 属性で誤検出する。`re.search(r"\bdata-lang=", html)` のように境界を付ける。
- **文字列テストで見た目の正しさを保証したことにしない。** CSS の規則が「存在する」ことは固定できても、
  それがカスケードで勝つか・意図した配置になるかは分からない。見た目は実ブラウザでの実測
  (要素の box・computed style)で確認する。
- **回帰テストは修正前のコードで落ちることを確認してから入れる。** 落ちないテストは何も守っていない。
- **関数を切り出して動かすテストの限界を知る。** 「要素取得や初期化そのものが無い / 落ちる」不具合は
  切り出し方式では見つからない。対象ページで実物を丸ごと起動するテストも持つ。
